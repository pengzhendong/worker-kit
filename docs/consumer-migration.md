# 现有 Worker 重新接入

目标是让现有业务逐个接入选定的原生前端与后端，同时继续使用 WorkerKit 的 HTTP、任务、存储契约。每个项目仍部署为一个 Worker。创建器用于新项目；它拒绝覆盖已有目录，不能直接对现有项目运行来完成迁移。

## 当前保留的兼容能力

本机消费项目引用检查确认，`/web`、`/web/session`、运行状态及 API 文档入口仍在使用。它们和旧单管理员认证继续保留；新模板不再复制旧 React UI。八套比较界面的组件体验继续用于选型，旧 React 的重复表格、表单、通知演示已退役；媒体例子仅在兼容示例的开发环境中加载。

| 能力 | 接入方式 | 迁移时需要保留或补齐 |
| --- | --- | --- |
| 页面、导航、通知、表单 | 选择一套原生前端组件 | 业务路由、主题偏好、加载/失败状态、手机导航 |
| API 请求与失效清理 | 使用 `/client`；旧 `/web` 路径继续兼容转发 | 401 清理用户数据，403/网络失败保留会话，取消旧请求 |
| 内容、媒体、用户 | 按项目需要选择 Payload 或 SonicJS | 原生认证、服务端角色校验、私有文件权限、现有用户迁移 |
| 业务任务与调度 | 复用 TaskManager 与现有调度端口 | DO 对象身份、计划、Alarm、去重、执行记录 |
| API Key、KV 设置、操作审计 | 保留现有业务接口，再逐项适配新页面 | 这些能力尚未全部接入新工作台，不能用 CMS 同名菜单替代 |
| 对外 API、代理、WebDAV、Queue、Workflow | 保留各项目原生 Worker 入口和路由 | 原有认证边界、事件导出、流式行为及外部协议 |

轻量项目是否需要 CMS 单独决定。已有登录或业务接口不因更换前端就强制迁移；需要更换认证时，先设计用户、角色、会话撤销和 API Key 的映射。

## 每个项目的迁移顺序

1. 记录当前 submodule 提交、lockfile、公开路由、认证方式、模块权限、定时入口和绑定清单。保存恢复所需的配置与数据备份。
2. 在项目自己的分支选择前端与后端。可在另一个临时目录生成同组合的参考项目，将普通布局、工作台和后端适配按需引入现有业务，不覆盖业务目录。
3. 保留 Worker 名、域名、D1/KV/R2、DO 绑定与对象命名。先接只读页面，再迁移写操作；数据库迁移使用该项目自己的显式迁移，不运行示例重置或管理员初始化脚本操作已有数据。
4. 保持原有 API 契约。逐项验证匿名访问、越权、同源/CSRF、登录与退出、令牌撤销、私有文件、媒体流和真实任务 Alarm，再验证桌面/手机布局。
5. 在父项目更新审核过的 submodule 指针和 lockfile，运行它自己的构建、类型检查、行为回归和部署 dry-run。具备部署授权后仍部署同一个 Worker，观察实际请求与运行错误。
6. 该项目验证完成后删除自己的旧页面和适配。所有消费项目都不再引用旧公共入口时，再删除 WorkerKit 的兼容层、旧依赖与专属回归用例。

源码快照的 `kit:sync` 只适用于创建器生成的 `vendor/worker-kit`。现有 submodule 消费项目继续用 Git 固定提交升级；两种升级方式不混用。回退先恢复旧代码指针和兼容配置，数据恢复遵循业务迁移方案，不自动删除新表或回滚生产数据。
